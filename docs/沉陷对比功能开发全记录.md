# 沉陷位移场对比：从原理、排障到功能落地全记录

- 日期：2026-10-06
- 系统：GeoMine3D 矿区三维地质可视化分析平台（Vue 3 + TypeScript + Three.js + FastAPI）
- 涉及模块：`SettlementManager`（位移场运行时）、`SceneCanvas`（场景装配与图例）、`SceneToolbox`（工具栏）、`AxisGizmoTool`（截图隐藏）、`remoteControl`（远程控制桥）
- 数据来源：开采沉陷预计计算成果按第 4 章共享建模网格组织的逐层顶点偏移场（`server/static/models/settlement/`）

## 一、功能原理

### 1.1 位移场的数据组织

沉陷对比的输入是两份文件：

| 文件 | 内容 |
|---|---|
| `vertex_offsets.index.json` | 元信息：每层位移段的字节偏移、顶点数、基线包校验和、统计值 |
| `vertex_offsets.bin` | 4.4 MB 连续二进制：每个地层一段 float32 三元组 `(dx, dy, dz)`，顺序与基线包对应层 GLB 的顶点顺序严格一致，单位为真实米，`dz` 负值表示沉降 |

本次接入的位移场覆盖 16,641 个共享网格节点中的 4,160 个采动影响节点，最大竖向沉降 3.20 m，最大水平位移 0.90 m，绑定对象为合并模型的 L01～L14 共 14 层、369,775 个表面顶点。

### 1.2 几何变形公式

设基线顶点位置为 `p0`，顶点位移为 `d`，变形进程 `t ∈ [0,1]`（0 = 沉陷前，1 = 沉陷后），沉陷显示夸大倍数为 `e`，则渲染位置：

```
p = p0 + e · t · d
```

位移直接作用在 `geometry.attributes.position` 上，跟随场景 Z 向夸张（`geoRoot.scale.z`，通常 20 倍）一同缩放。启用对比时把基线顶点备份一次，此后每帧只是 `base + k·offset` 的线性组合，关闭对比时从备份恢复。

### 1.3 为什么是"单模型 + 顶点位移"，而不是沉陷前后双模型叠加

两条硬理由：

1. **深度冲突**：本矿区模型 67% 以上的顶点在沉陷前后严格共面，沉陷前后两套模型同屏叠加必然大面积 z-fighting；
2. **材质生命周期**：系统的高亮管理器与图层透明度控制会整体替换材质。若把位移写在着色器注入（`onBeforeCompile`）里，材质一被替换位移就丢失。直接改几何则与剖切、炸开、拾取、高亮等既有工具天然兼容。

### 1.4 位移量着色设计

按竖向位移量（`dz` 模式）或水平位移幅值（`magnitude` 模式）归一化后映射 HSL 色带：深青（无位移）→ 黄红（最大沉降）。着色必须启用材质的 `vertexColors` 并提供逐顶点颜色属性；面板同时显示最大沉降、最大水平位移、绑定层数与顶点数，绑定失败逐条给出原因。

## 二、接入与排障过程（bug 狩猎实录）

功能的最终形态是"边截图、边排障、边修系统"逼出来的。按时间线记录如下。

### 2.0 前置：远程控制桥（背景工程）

手工在浏览器里拖轨道、拉滑块无法稳定复现同一机位，于是先给系统装了一个**远程控制桥** `remoteControl.ts`：生产构建下访问 `?remote=1` 时把场景引擎暴露到 `window.__geomine`，提供相机球坐标定位（`setView`）、地层颜色/透明度/显隐、三轴剖切、炸开、白底 PNG 导出（`capture`，支持超采样与临时隐藏坐标轴测）等能力。后续所有排障与论文配图都通过它完成。

### 2.1 坑一：相机越调越低、钻进模型底部

**现象**：用坐标拖拽模拟轨道旋转，重置视角后稍微一拖，相机就翻到模型底下。

**定位**：不是拖拽方向反了，而是**滚轮缩放步长过大**——对 12.8 km 尺度的模型，一次 `scrollY: -240` 的 dolly 直接把相机推过了观察目标，落到了模型另一侧下方。

**解决**：以"重置视角/适配全场景"为唯一基线，缩放不盲调；后来桥接里的 `setView` 直接用球坐标（方位角 + 仰角 + 距离系数）定位，彻底摆脱拖拽。

### 2.2 坑二：参数改了，截图没反应

**现象**：通过 Pinia store 修改地层颜色/显隐后立即截图，拿到的仍是旧状态；隔一次调用才发现界面变了。

**定位**：Vue 的 watcher 是异步刷新（微任务队列），"改状态 → 同一帧内截图"拿到的是上一帧。

**解决**：状态变更后显式 `await` 数百毫秒再做渲染截图。这个坑后来在沉陷参数（time/exaggeration/colorMode）上再次出现，处理方式相同。

### 2.3 坑三（着色核心 Bug A）：vertexColors 开关未联动

**现象**：切到"沉降"着色模式，模型毫无变化。

**定位**：`applyVertexColors` 忠实地把颜色写进了几何的 `color` 属性，但分层 GLB 的材质 `vertexColors` 默认为 **false**——three.js 在该开关关闭时根本不读取颜色属性，写了等于没写。

**修复**：`applyVertexColors` 中按着色模式同步材质 `vertexColors` 开关（着色模式 = true，原始模式还原为加载时的值）。

### 2.4 坑四（着色核心 Bug B）：颜色属性是 Uint8Array，浮点全被截断

**现象**：开了 `vertexColors` 后模型不是呈现色带，而是**通体发白、从场景里"消失"**。

**定位过程**（本功能最典型的一次二分排查）：

1. 先怀疑状态没生效——直接调 `SettlementManager.setColorMode('dz')`，探查返回 `colorMode: 'dz'`、`vertexColors: true`，颜色属性存在且尺寸正确（32,826 × 4）；
2. 读属性值：全部为 0；
3. **决定性实验**：直接向属性数组写 `0.777` 再读回——得到 `0`；进一步查 `arr.constructor.name`，结果是 **`Uint8Array`**！

**根因**：分层 GLB 自带的 `COLOR_0` 顶点色属性是 **Uint8 归一化**类型。旧代码按 Float32 语义往里写 0～1 浮点数，全部被截断成 0；且旧代码只在"属性不存在或尺寸不符"时才新建属性，对这个尺寸恰好匹配的 Uint8 属性直接沿用，于是永远写不进去。

**修复**：着色时检查现有颜色属性的数组类型，非 `Float32Array` 一律替换为新建的 Float32 `BufferAttribute`（RGBA），写入后再挂回几何；恢复"原始"模式时把**原始属性对象**（连同其类型与归一化语义）原样挂回，而不是按 Float32 假设拷贝数值——否则 Uint8 里存的 0～255 值会被错当成 0～1 造成过曝。

### 2.5 坑五：关闭对比后颜色不还原

**现象**：一键关闭沉陷对比后，位置回到基线了，模型却停留在上一次的着色状态。

**定位**：`restoreBase` 只还原了顶点位置；着色期间被替换的颜色属性和被打开的 `vertexColors` 开关无人负责恢复。

**修复**：`restoreBase` 与 `applyVertexColors` 对称——逐 mesh 把原始颜色属性对象挂回（无原始属性则删除），并把 `vertexColors` 还原为绑定时刻的值。端到端验证：开 → 沉降着色 → 关，模型回到原始米黄色（材质色 `#d9c7a3`、`vertexColors: false`）。

### 2.6 坑六（视觉层）：白底"鬼影"与看不见的盆地

两个渲染观感问题一度干扰排障判断：

1. **鬼影**：白底截图里模型轮廓外有一圈灰色重影。逐层隐藏、绕过后期合成器直渲染都排除后，定位为**材质半透明**（分层 GLB 材质 opacity 0.95）的透明排序伪影——把演示用的地层统一设为不透明后消失；
2. **盆地不醒目**：真实最大沉降仅 3.2 m，叠加 Z 向 20 倍显示夸张后在 12.8 km 尺度下仍不显眼。按工具箱的既定设计启用**沉陷显示夸大 30 倍**（叠加基准夸张后竖向共约 600 倍），并在论文图注与系统图例中明确标注，避免误读为真实幅度。

### 2.7 排障方法论小结

- **决定性实验优于猜测**：写 0.777 读回 0 一步就锁定了属性类型问题，比反复读代码快得多；
- **z 范围不是好探针**：先用各层顶点 z 的 min/max 验证变形，结果"没变化"其实是最大沉降点不在极值顶点上——改用"逐顶点数组写读回"和渲染对比才可靠；
- **改状态与截图之间必须等框架刷新**（Vue watcher 异步）；
- **渲染问题逐层二分**：绕过 EffectComposer 直渲染 → 排除后期管线；逐层隐藏 → 排除几何；材质/属性直接探查 → 锁定根因。

## 三、工具栏一键开关与场景图例

功能修好之后，把操作路径从"开面板 → 翻开关"升级为一键式：

1. **导轨一键开关**：`SceneToolbox` 的 `ToolGroup` 新增 `toggleable` 标志。点击沉陷导轨按钮时发出 `rail-toggle` 事件由宿主直接开/关功能：启用时自动展开参数面板，禁用时收起；按钮带铜色圆点表示激活态。面板内的"启用沉陷对比"开关仍可独立控制，两种入口状态互通。
2. **场景图例**：启用对比时场景左上角显示悬浮图例——当前变形进程（t=xx%）、位移色标（渐变条 + "0" 到 "竖向位移 ≤ 3.20 m" 或 "水平位移幅值 ≤ 0.90 m"）、沉陷夸大倍数与叠加的 Z 向倍数。着色模式关闭时只显示状态行。有了图例，演示与截图时不会把夸大后的形态误读为真实幅度。

端到端验证路径：加载合并模型 → 点沉陷按钮（启用 + 面板展开 + 图例出现）→ 点"沉降"着色（色标出现、模型着色）→ 再点沉陷按钮（禁用、面板收起、图例消失、模型完全回到原始显示）。

## 五、经验教训

1. **先查属性类型再写字段**：three.js 里同名 `color` 属性可能是 Float32 也可能是 Uint8 归一化（GLTF 的 COLOR_0 组件类型决定），写入前看一眼 `constructor.name` 能省掉一轮排查；
2. **框架的异步刷新是自动化验证的头号假阴性来源**：改 Pinia 状态后必须让微任务跑完再断言；
3. **排障要有一锤定音的实验**：直接写值读回、绕过某一层管线、逐层隐藏——每一步排除一半可能；
4. **`git stash` 会吞掉所有未提交修改**（且默认不收未跟踪文件）：批量改动要及时提交；本次开发记录写成文档，也是为了防止"改动只在 stash/dist 里、源码里找不到"这类状态再次发生；
5. **渲染观感问题要与数据问题分开排**：鬼影（半透明伪影）和盆地不醒目（真实量级小）都不是代码 bug，混在一起会带偏方向。
